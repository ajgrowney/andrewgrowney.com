## Page 1: Build My Bracket (/mm-2026/bracket)

### Purpose
Let users **apply a classifier** to fill out their bracket. This is the payoff—using a trained model (theirs or a preset) to make predictions.

### Blog Connection
> "If we can come up with a consistent rule to pick the winner of a game, then we just have to use that rule 63 times!"

### Key Concepts Visualized
- **Classification**: Each slot is a prediction (Team A vs Team B)
- **Probability**: Show win probability percentages, not just picks
- **Joint Probability**: Cascading predictions through dependent matchups

### Features

#### 1. Model Loading
- **Preset Models**: "Andrew's 2026 Model", "Seed-Only (Rule #2)", "Coin Flip (Rule #1)"
- **Custom URL**: Load tf.js model from user-hosted location (from Model Builder export)
- **Local Upload**: Drag & drop model.json + weights

#### 2. Slot Interaction
- **Click empty slot**: "Slot Insights Drawer" comes out with:
  - Probability breakdown of all potential teams that could make this slot and their respective percentage (e.g., Duke 87.2% vs FGCU 12.8% for a Round of 32 slot, )
  - Feature comparison table (the inputs used by the model are highlighted)
  - "Auto-fill" button to accept prediction
  
- **Click "Fill Through" on deeper slots**: 
  - Computes all dependent matchups recursively
  - Shows joint probability for that team reaching slot
  - Example: "Duke has 34.2% chance to reach Final Four (87.2% × 64.1% × 61.2%)"

#### 3. Feature Inspector Panel (Collapsible)
When a matchup is selected, show:

### Technical Implementation

## Page 2: Model Builder (/mm-2026/model)

### Purpose
Let users **define, fit, and export their own classifier**. This is where they experience feature engineering, training data selection, browser-side fitting, and see how a real coefficient-based model changes with different historical seasons.

### Blog Connection
> "As we were selecting the statistics that we wanted to use in our team value function, we were going through the practice of what is called **feature engineering**."
>
> "Finding the best weights to maximize the number of correct predictions is the process of **training (aka fitting)** our model."

### Key Concepts Visualized
- **Feature distributions**: Preview how each live 2026 feature behaves across the field before using it
- **Input dimensions**: Show selected stats moving into the classifier as explicit dimensions
- **Manifest-driven training**: Read the published browser training manifest before loading season datasets
- **Matchup engineering**: Use the exported historical diff-format matchup rows as the browser fitting dataset
- **Classifier weights**: Fit logistic-regression coefficients in-browser and inspect which features matter most
- **Preview loop**: Run the fitted classifier through matchup and bracket previews before export

### UX Flow - 3 Tabs

#### Tab 1: Select Features

- Limit the builder to `Prediction` models for now
- Support exactly one classifier family initially: `Logistic Regression Classifier`
- Plot a live distribution for one selected feature across the 2026 field
- Let users mark features as selected and show them moving into the classifier as explicit input dimensions
- Pull the selectable feature list from the live training manifest `feature_order`
- Reinforce the YDKYK point that more features is not automatically better

#### Tab 2: Build Matchup Dataset

- Load the live browser training manifest from `data/web/training/manifest.json`
- Let users choose which historical seasons to include and whether to use regular-season games, tournament games, or both
- Preview the exported diff-format matchup rows from `data/web/training/historical_v1/{season}.json`
- Show the exact feature order and label convention used for training
- Keep preprocessing fixed and explain that the browser normalizes those matchup deltas before fitting

#### Tab 3: Preview & Export

- Fit a logistic classifier in-browser from the currently selected seasons, sources, and features
- Preview head-to-head probabilities for a selected matchup using the fitted runtime classifier
- Run that same classifier through the 2026 bracket graph for a tournament-level sanity check
- Surface simple train/validation metrics and strongest coefficients before export
- Export a JSON runtime config that includes weights, label definition, manifest metadata, selected seasons, source filters, and preprocessing notes

### Technical Implementation
```js
// Load manifest and selected season datasets
const manifest = await fetchJson('data/web/training/manifest.json');
const seasonData = await fetchJson(manifest.training_files['2025']);

// Convert raw diff rows into the normalized representation used by runtime inference
const normalizedRows = seasonData.examples.map((example) =>
  selectedFeatures.map((featureKey) => normalizeFeatureDifference(featureKey, example.x[featureIndexMap[featureKey]]))
);

// Fit a browser logistic classifier with gradient descent
const fitted = fitBrowserLogisticModel({
  examples: seasonData.examples,
  featureOrder: manifest.feature_order,
  selectedFeatures,
  labelDefinition: manifest.label_definition
});

// Export a runtime config with provenance
downloadModelConfig({
  feature_set: manifest.feature_set,
  label_definition: manifest.label_definition,
  training_manifest: {
    manifest_path: 'data/web/training/manifest.json',
    seasons_available: manifest.seasons
  },
  training_filters: {
    seasons: selectedYears,
    include_regular_season: includeRegularSeason,
    include_tournament: includeTournament
  },
  weights: fitted.weights,
  bias: fitted.bias
});
```

### Recommended Export Strategy

- Export the full `TeamSeasons_2026.csv` for training and analysis
- Export lean JSON indexes for browser routing and search
- Export a compact feature store for inference-only pages
- Export rich per-team JSON only for pages that need deep drill-down content
- Keep model availability and compatibility in a standalone manifest instead of hardcoding it in the site
